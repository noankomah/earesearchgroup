# Keep the existing Google indexing during the Django launch

The public site remains `https://earesearch.org/`. GitHub is the source repository, not the website address. Changing the backend to Django does not require changing indexed `.php` URLs: Django can serve those paths without executing PHP.

## Preserve the existing site identity

- Keep the same domain, HTTPS scheme and preferred non-www hostname.
- Keep the Search Console property and its verification. Preserve existing DNS TXT verification records when changing A/AAAA records. If verification used an HTML file or meta tag, transfer that exact file/tag before launch; do not invent a replacement token.
- Keep the sitemap at `https://earesearch.org/sitemap.xml`. It is generated by Django and uses the original public page addresses plus published content.
- Keep original article slugs, published content, images and downloads when transferring data. A working URL with an empty/error page can still be treated as a soft 404.
- Do not redirect every missing address to the homepage. Use a permanent redirect only where there is a relevant replacement; otherwise a real 404 is correct.

The old About addresses under `/views/About/` are retained by Django so previously indexed links can continue to show the matching section. Existing publication and opportunity query-string addresses remain supported.

## Before switching DNS

Import the real content and uploads, including the founder story. The initial seed alone does not supply founder-story/publication/opportunity records. Check public content while logged out. Do not publish an empty page merely to make a status check return 200. The sitemap excludes unavailable content and empty placeholders.

Enable the real TLS certificate and keep public pages crawlable. The normal robots file blocks only administration and the team workspace. Remove any temporary whole-site `noindex` or crawl block used during staging. Keep a staging hostname private or noindex until launch.

## After the site is live

Check the old URLs, for example:

```bash
for route in / /views/About/who-we-are.php /views/About/governing-board.php /views/About/our-team.php /views/About/founder-story.php /views/About/contact-us.php /publications.php /sitemap.xml; do
  curl --silent --output /dev/null --write-out "$route: %{http_code}\n" "https://earesearch.org$route"
done
```

A published founder story should return 200; absent/unpublished content should not be faked. Check known article URLs and their images too.

In the existing Search Console property:

1. Inspect a few affected addresses with the live URL test.
2. For pages restored to real content, use Request indexing and Validate fix where available in the 404 / Soft 404 reports.
3. Check the existing `/sitemap.xml` submission and resubmit that same address if useful.
4. Monitor the report and server logs while Google recrawls. Reports can lag behind the live site.

Keeping URLs avoids an unnecessary URL migration, but it cannot prevent recrawling or guarantee immediate recovery of pages removed during the outage. A sitemap helps discovery; it does not guarantee indexing or rankings. No Search Console Change of Address is needed when the domain is unchanged.

## Unrelated URLs reported from the old cPanel hosting

The provided examples (`/brand/manufacture/...htm`, `/species/accessory/...htm`, `/taxonomy/byproduct/...htm`) are not EARG pages in this application. Their appearance in Search Console is consistent with unwanted URL discovery or historical injected spam, but the report alone does not establish how access occurred or whether the old server remains compromised.

Do not restore these addresses, redirect them to the homepage, include them in the sitemap, or block their recrawling in robots.txt. The Django application returns genuine 404s for them, including to Googlebot. The old reporting count can remain until Google recrawls and updates its reports.

Deploy the reviewed Django code rather than copying the old hosting web directory wholesale. Transfer only the intended structured content and validated uploads; do not bring old server scripts, .htaccess files or unfamiliar executable files into the new runtime. Preserve/control the registrar, DNS, hosting and Search Console accounts; a new backend cannot fix unauthorized access to those accounts.

Review Search Console Security issues and Manual actions for any outstanding findings. If a finding exists, follow the documented cleanup and review process after the actual issue has been fixed. No claim about the old server's current security can be made from these screenshots alone.

References: https://support.google.com/webmasters/answer/2445990 and https://support.google.com/webmasters/answer/9044101
